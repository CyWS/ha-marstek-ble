# Marstek BLE entities

Entity availability is product-specific. The integration selects a product runtime from the discovered/persisted device type and only exposes entities supported by that product profile.

## Validation status

Jupiter-C Plus has been exercised against real hardware on the current multi-product code path.

Venus E has **not** been revalidated on physical hardware after the multi-product refactor. Its compatibility is currently supported by automated regression/unit tests that compare the migrated runtime and entity behavior with the intended behavior of the original integration. The Venus entities and controls described below are therefore implemented and expected to work, but remain hardware-unverified in this fork.

## Venus E

### Monitoring

Typical Venus entities include:

- battery voltage, current, power, state of charge, state of health, temperatures, and cell voltages;
- charged/discharged energy counters and capacity values;
- grid, solar, and output power;
- device, firmware, network, and configuration information; and
- connectivity/state binary sensors.

### Controls

Venus remains the only product with enabled write/control platforms. The current implementation exposes:

- `Output 1 Control`, `EPS Mode`, `AC Input`, `Generator`, and `Buzzer` switches;
- an `Operating Mode` select with **Self-Consumption** and **Manual** options;
- `Charge Mode` and `CT Polling Rate` selects; and
- `Reboot`, fixed power-mode, AC-power, and total-power buttons.

The current code does **not** expose AI Optimization as a BLE control.

Write controls use Venus command semantics and must not be assumed to apply to other Marstek products. Because no physical Venus unit was available during this release preparation, the control behavior is covered by automated tests but has not been confirmed end-to-end against current hardware/firmware.

## Jupiter-C Plus

Jupiter support is read-only in the first multi-product release. No Jupiter `button`, `switch`, or `select` entities are created.

### Main device

The Jupiter main device exposes modeled telemetry such as:

- battery state of charge, stored energy, voltage, current, signed battery power, state, limits, state of health, and temperatures;
- AC output power and qualified grid-connection state;
- grid voltage/frequency and inverter diagnostics;
- four PV inputs with connection state plus available voltage/current/power telemetry;
- PV generation and discharge-energy counters;
- MPPT state/diagnostics and PV-input-active flags;
- firmware/identity diagnostics; and
- compact event-history diagnostic records.

Some reverse-engineered fields are explicitly tentative or carry `Unverified` in their friendly name. Those entities are diagnostic observations, not vendor-confirmed semantics.

In particular, `Surplus Feed-In Active Unverified` must not be treated as a confirmed representation of the user-facing surplus-feed-in configuration.

### Battery child devices

Jupiter-C Plus battery packs are represented as child devices:

- position 0: base battery;
- positions 1–3: expansion batteries.

Only populated positions are exposed. Position is used as the stable device identifier so an expansion retains its Home Assistant identity across restarts/reloads as long as it remains in the same physical slot.

Pack entities include diagnostic cell-index/cell-voltage summaries and pack status where available from the modeled telemetry.

## Polling cadence

Fast and medium polling intervals are configurable, but the actual commands are product-specific.

For Jupiter-C Plus the current read-only schedule is:

| Tier   | Commands                         |
| ------ | -------------------------------- |
| Fast   | `0x03`, `0x14`                   |
| Medium | `0x0D`, `0x08`, `0x04`, `0x13` |

Jupiter commands `0x1A`, `0x1C`, `0x21`, `0x22`, and `0x24` are intentionally not polled because their semantics are absent or unresolved.

Venus uses its own runtime-owned polling schedule and retains the telemetry/configuration commands required by its existing entity set. That schedule is regression-tested but has not been revalidated on physical Venus hardware in this fork.

## Entity identity and availability

The integration uses product-profile entity plans to create sensor and binary-sensor entities. Repeated Jupiter records additionally carry presence information so already-created expansion entities can become unavailable without being renumbered when a pack disappears.

Entity IDs are generated by Home Assistant from the device/entity names and may therefore differ between installations. Automations should prefer the actual entity IDs shown by Home Assistant rather than hard-coded examples from documentation.
